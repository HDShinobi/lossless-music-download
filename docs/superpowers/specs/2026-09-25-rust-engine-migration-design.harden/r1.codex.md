[SEVERITY: major]
LENS: completeness
LOCATION: §3.1 Init; §6 Rollback
ISSUE: The spec does not define compatibility or migration for existing extension installs, credentials, grants, provider settings, and other Go-engine data, nor whether that data remains safe after rollback.
SUGGESTION: Define the persisted-data compatibility contract, migration and failure behavior, and upgrade/rollback tests using a populated v0.9.1 profile.

[SEVERITY: major]
LENS: ambiguity
LOCATION: §3.4 Coexistence flag
ISSUE: Selecting Go or Rust “per call” leaves stateful workflows undefined when initialization, request IDs, cancellation, leases, authentication, and downloads cross engine boundaries or the flag changes concurrently.
SUGGESTION: Make engine selection process- or session-scoped, define when it may change, and require teardown or isolated state before switching engines for A/B runs.

[SEVERITY: major]
LENS: completeness
LOCATION: §6 scripts/sync-upstream.sh; Layer 1 “byte-identical target, 1 temporary LM-FORK”
ISSUE: The sync design does not specify how a local patch inside the inherited rust_backend tree survives --apply, conflicts with upstream edits, or is retired, so the central sync mechanism can silently erase or overwrite the sole LM-FORK.
SUGGESTION: Specify the three-way inputs and conflict rules, preserve and verify registered local patches before advancing the baseline, and define the exact retirement path after upstream merges.

[SEVERITY: major]
LENS: completeness
LOCATION: §3.1 EngineBridge; §7 phase 2
ISSUE: The normative bridge contract is incomplete: “~25” plus 7 changed and 2 removed methods accounts for about 34, while phase 2 requires 41, without an exhaustive mapping of the remaining methods, result shapes, or error semantics.
SUGGESTION: Add a complete 41-method legacy-to-Rust contract table covering arguments, success shape, error shape, state effects, cancellation, and unsupported behavior.

[SEVERITY: major]
LENS: completeness
LOCATION: §4 Layer 3 — DLNA server in Kotlin
ISSUE: The DLNA lifecycle omits ownership and behavior for partial startup failure, repeated start/stop, coroutine or Ktor failure, LAN address or network changes, and Android process/background termination.
SUGGESTION: Define an explicit stopped/starting/running/stopping/failed state model, rollback and cleanup invariants, network-change policy, process-lifetime owner, and status/error behavior.

[SEVERITY: minor]
LENS: testability
LOCATION: §8 E2E matrix on device; Metrics vs v0.9.1
ISSUE: “Matrix passes” does not state whether every source-format-flow combination is required or give observable pass criteria, while cold-start and RAM measurements have no comparison rule.
SUGGESTION: Publish the required test cases with expected outcomes and evidence, and define baseline methodology plus decision thresholds or explicitly mark cold-start and RAM as informational.
